024.11: Claude Code 2.1.318 - תיקון רגרסיית אובדן-שיחה מ-2.1.314, אזהרת תפוגת login, ו-effort נפרד ל-fork של mod+

מה זה ולמה כאן

שוחרר ב-4.11 (חצות UTC). גרסת תיקונים עמוסה עם כמה פנינים, יום אחרי 2.1.317 שכוסתה כאן אתמול.

התיקונים שכדאי לדעת עליהם

הבולט: תיקון לרגרסיה מ-2.1.314 שבה --continue איבד לפעמים את השיחה הקודמת אחרי שנגמרו הנסיונות של tool call פגום - אם איבדת שיחה בשבוע האחרון, זו הסיבה. תיקון נוסף עם משמעות אבטחה: פרומפטים של הרשאות נענו על ידי הקשות שהוקלדו מיד אחרי שליחת הודעה או לפני שפרומפט איטי הופיע - כלומר הקשה תועה יכולה הייתה לאשר פעולה. וסדרה על כתיבת config: על home משותף ברשת, /logout, claude mcp remove ושינויי trust דיווחו הצלחה בלי שנשמר בפועל; claude mcp add/remove ממתינים כעת לנעילת הקובץ.

החדש

effort ל-$.model.fork של mod - עבודת-צד מהירה יכולה לרוץ ב-low גם כשהסשן ב-high (השלמה להיררכיית המאמץ מ-2.1.316). loginExpiresAt ב-claude auth status וב-JSON של claude -p, ואזהרת stderr החל מ-10 ימים לפני תפוגת sign-in - חשוב ל-CI שמתחיל לקרוס "בלי סיבה". assume_role על upstreams של mantle ב-gateway לייחוס עלויות AWS פר-מפתח.

חיבור אפשרי לפרויקטים שלך: אם הרצת --continue על סשנים של מענה בימים האחרונים ונתקלת באובדן הקשר - שדרג ל-2.1.318 ונסה שוב. ואם יש לך jobs של claude -p ב-CI של dorgames, הוסף קריאת credential_expires_at ל-healthcheck במקום לגלות על תפוגה בלילה.

מה זה ולמה כאן

late catch: נכנס ל-release notes של ה-API ב-2.11 ולא נתפס בסריקה; עדיין בתוך 48 שעות. זה שינוי ארכיטקטוני אמיתי לכל בונה סוכנים על Claude: ה-API שומר את השיחה בצד שרת, ובקשות הבאות שולחות רק את ההודעות החדשות - time to first token יורד ככל שהלולאה מתארכת.

הפרטים הטכניים

בטא מאחורי ה-header message-threads-2026-08-12. thread פג 5 דקות אחרי הבקשה האחרונה ונמחק עד שעה אחרי השימוש האחרון. זמין ב-Claude API, ב-Bedrock (Claude Platform on AWS), ב-Google Cloud (Anthropic managed) וב-Microsoft Foundry. הכיוון ברור: לולאות סוכן ארוכות (עשרות תורי כלים) לא צריכות לשלוח מחדש את כל ההיסטוריה בכל תור - עם העלות הטוקנית והשהייה שבכך.

איך לקרוא את זה

שים לב למתח המעניין: זו גם הפחתת-עלות ל-Anthropic (cache ממילא), אבל היא הופכת את ה-API מ-stateless טהור ל-stateful לזמן קצר - מודל איום שונה, והחלטת עיצוב שצריך להיות מודעים אליה (מה קורה לשרשרת אם ה-thread פג אמצע ריצה? נדרש fallback לשליחה מלאה). התיעוד ממליץ להתייחס ל-thread כאופטימיזציה, לא כאחסון.

חיבור אפשרי לפרויקטים שלך: אם מענה או Podcasto מריצים לולאות סוכן ארוכות על ה-Messages API - threads מורידים גם עלות טוקנים (במיוחד רלוונטי אחרי איחוד המכסות מכרטיס אתמול) וגם TTFT. התכנון הנכון: נסה thread כנתיב מהיר עם fallback מלא לשליחה מחדש אחרי פקיעה - ותמדוד את ההפרש על המשימה הכי ארוכה שלך.

מקורות: Claude Platform release notes (רשומת 2.11) · תיעוד message threads

043.11: Dependabot לומד Agent Package Manager - skills, פרומפטים והוראות של סוכנים מקבלים PR-י עדכון כמו תלויות+

מה זה ולמה כאן

GA ב-github.com לכל התוכניות (3.11; ל-GHES ב-3.24): Dependabot פותח pull requests לעדכון תלויות git המוצהרות ב-apm.yml ומייצר מחדש את apm.lock.yaml. כלומר - ה"תוכן" של הסוכנים שלך (skills, prompts, instructions) נהיה תלות מנוהלת עם היסטוריית עדכונים, בדיוק כמו npm או pip.

למה זה משנה

עד היום, עדכון פרומפט של סוכן היה "למשוך מהריפו כשזוכרים". עכשיו יש מנגנון סטנדרטי עם lock file, PR מתואר, ו-diff שניתן ל-review לפני merge - כולל האופציה לראות מה השתנה בהוראות של הסוכן שאתה מריץ לפני שהוא משתנה אצלך. שים לב לגבול: התמיכה מכסה version updates בלבד, לא security updates - פרומפט זדוני לא ייתפס כאן.

איך לקרוא את זה

זה עוד צעד בהפיכת הפרומפט לחלק משרשרת האספקה - עם כל מה שלמדנו השבוע (תוסף Cursor, "דליפת" Mythos): גם טקסט הוראות הוא artifact שמגיע ממקור חיצוני, גם לו צריך גרסאות, ביקורת ו-diff. מי שמאמץ את הדפוס מוקדם מקבל את ה-review סביב שינויי פרומפט בחינם.

חיבור אפשרי לפרויקטים שלך: אם מענה או dorgames מושכים skills/פרומפטים ממקורות חיצוניים - העבירו אותם ל-apm.yml עם Dependabot schedule; תקבלו PR מסודר במקום הפתעות. ול-Podcasto: lock file על הוראות ה-agent pipeline שלך פירושו שאתה יכול להצביע בדיוק איזו גרסת-הוראות הפיקה איזה תוכן.
