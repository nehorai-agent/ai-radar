01Copilot for JetBrains: MCP לא חייב להתחיל לבד, וצריך IDE 2025.2 לפחות+

מה פורסם

ב-10.10 ב-18:53 UTC GitHub פרסמה עדכון לתוסף Copilot ב-JetBrains. נוספה הגדרה שמבטלת הפעלה אוטומטית של שרתי MCP עבור Copilot ו-Claude. בנוסף, מנהלי Enterprise יכולים לבחור מודל agent זמין כברירת מחדל לשיחות חדשות, בלי לעקוף בחירה מפורשת של המשתמש ב-model picker.

למה הפרט הזה חשוב

שרת MCP מוגדר ושרת MCP פעיל אינם אותו מצב. ההגדרה החדשה נותנת שליטה בזמן ההפעלה, אבל הפוסט לא אומר שהיא מבטלת הרשאות, עוצרת שרת שכבר פועל או מוחקת credentials. אם רוצים לבדוק אותה, צריך לבדוק startup בפועל בסשן חדש, ולא להסיק ממצב checkbox שכל הפעולות נחסמו.

גם ברירת המחדל של המודל חלה על שיחה חדשה; היא אינה תיאור של החלפת מודל בכל שיחה קיימת. ההבחנות האלה מונעות בדיקה שנראית מוצלחת רק מפני שהסתכלנו על סשן שלא הושפע מהשינוי.

שינויים נוספים עם משמעות מעשית

פעולת Fix בתפריט diagnostics פותחת inline chat ומבקשת תיקון: agent mode כשזמין, ask mode אחרת. זו בקשת תיקון, לא הוכחה שהקוד תוקן או עבר בדיקות. הודעות chat מקובצות לפי turn, אפשר להעתיק או לערוך הודעות משתמש, ונוסף Switch Account לצד תוויות ברורות יותר לחשבונות מחוברים.

GitHub מציינת שיפור אמינות סביב language server, החלפת model/provider, MCP config, customization refresh, שינוי קבצים ו-worktrees. אין בפוסט פירוט תקלות, מדידה או רשימת גרסאות שנפגעו, ולכן לא מוצגת כאן הבטחה לביצועים.

תנאי התאימות שלא כדאי לפספס

התמיכה ב-JetBrains IDE 2025.1 הסתיימה. נדרש IDE 2025.2 או חדש יותר כדי להשתמש בתוסף. הפוסט מפנה לתוסף העדכני בלי לציין מספר build מדויק, ולכן לא ייחסתי את השינויים לגרסה מספרית שלא אומתה.

החיבור אליך: אם אתה עובד על מענה, podcasto או dorgames בתוך JetBrains, קודם בדוק גרסת IDE, ואז את חשבון Copilot ואת ה-startup של MCP בסשן חדש. אין לי ראיה שאתה משתמש ב-JetBrains, ולכן זו בדיקה מותנית, לא המלצה לעבור IDE. גם במוצר שלך, הפרד בין "הכלי מוגדר", "הכלי התחיל" ו"מותר לו לבצע פעולה".

מה לא נעשה

הפוסט הרשמי נקרא כולו. התוסף לא הותקן, לא נבדק בחשבון, לא שונתה הגדרה ולא הופעל שרת. לא נמדדו הביצועים ולא אומתה גרסת Marketplace מסוימת.

02Styx 0.4.10: token רחב ב-production, אישור נפרד לכל פקודה+

מה השתנה בפועל

Styx הוא desktop wrapper ל-CLI של סוכני קוד. release 0.4.10 מ-10.10 כולל שינוי ל-production targets שה-provider שלהם אינו נותן credential מצומצם לכל grant: write, deploy ו-delete מוגבלים ל-once, עם אימות של מערכת ההפעלה בכל אישור. המטרה היא שאישור של שעה לא יאפשר עוד פקודות production באותו scope בלי שאלה נוספת.

ב-diff של policy engine ב-PR39, הוספת credentialScoped מגבילה את משך האישור ל-once ומונעת שימוש ב-always grant קיים לבקשה הזאת. ה-issue מתאר Vercel, Supabase, GitHub ו-Cloudflare עם token רחב. קריאות ויעדים שאינם production אינם אותו מקרה. בדקתי קוד ותיעוד, אבל לא התקנתי או הרצתי בדיקת עקיפה.

הגבול: guardrail, לא sandbox

תיעוד האבטחה אומר מפורשות שהסוכן רץ כמשתמש המקומי ויכול לגשת לקבצים ולרשת. ה-shims תופסים שמות CLI מסוימים; הם אינם חוסמים CLI בנתיב מלא, git push עם credentials הרגילים או SDK/API עם token שהסוכן מצא. בחלק מהעקיפות מוצגת אזהרה, לא חסימה.

גם grant של once אינו token של once. ב-GitHub, Supabase ו-Vercel הפקודה מקבלת את ה-token השמור עם כל הרשאותיו. revoke מפסיק מסירה דרך Styx, אבל אינו מבטל את ה-token אצל הספק. ולכן אין כאן הוכחה שהסוכן לא יכול להעתיק credential או לעבוד מחוץ למסלול.

פער בתיעוד

דף Approve a request עדיין אומר באופן כללי שפקודות בתוך scopes של grant פועלות בלי לשאול עד פקיעתו. ה-release, issue והקוד מוסיפים חריג once ל-production writes על credential לא מצומצם. לפני הסתמכות על המוצר צריך לוודא מה גרסה מותקנת עושה בפועל. גם Windows ו-Linux מוגדרים beta; לפי תיעוד security, Windows אינו code-signed וארטיפקטי Linux אינם חתומים.

החיבור אליך: לפקודות deploy של מענה או podcasto, ההבחנה בין אישור לפקודה לבין הרשאות ה-token היא לקח שימושי. אפשר לאשר פעולה אחת ובכל זאת למסור מפתח רחב מדי. זה אינו צורך להתקין Styx או לתת לו keys; לא נעשה שינוי באף פרויקט. אם בוחנים wrapper, בדיקת הנתיב מחוץ ל-wrapper חשובה לא פחות מבדיקת חלון האישור.
