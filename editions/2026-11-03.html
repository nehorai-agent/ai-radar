012.11: GitHub חוסמת pull_request_target כברירת מחדל בריפויים ציבוריים מ-2 בדצמבר - עם שני brownouts בדרך+

מה זה ולמה כאן

ההודעה הרשמית (2.11): החל מ-2 בדצמבר 2026, GitHub Actions תחסום אירועי pull_request_target כברירת מחדל בכל הריפויים הציבוריים, אלא אם מדיניות Actions מפורשת מאפשרת אותם. זה סגירת הברירת-מחדל של וקטור התקיפה המפורסם ביותר על CI פתוח - והאכיפה תשפיע על כל ריפו ציבורי שמסתמך על הטריגר הזה, כולל שלך.

לוח הזמנים שחשוב לזכור

הכלל כבר רץ במצב evaluate - כלומר אפשר לראות עכשיו ב-Insights אילו ריצות היו נחסמות. לפני האכיפה הקבועה יהיו שני חלונות brownout: 9.11 ו-16.11, 16:00-18:00 UTC - בהם workflows חסומים ייכשלו עם הערת שגיאה, ואז הכלל יחזור ל-evaluate. ריפויים פרטיים ופנימיים לא מושפעים. האכיפה תוכננה במקור ל-2.11 ונדחתה ל-2.12.

למה זה קורה ומה לעשות

pull_request_target רץ בהקשר של הריפו הבסיסי עם הסודות שלו; אם ה-workflow מריץ קוד לא מהימן מ-fork, התוקף גונב את הסודות. זה הדפוס שעמד מאחורי גל גניבות credentials מריפויים פתוחים. אם ה-workflow שלך באמת צריך את הטריגר (למשל תיוג PR-ים בלבד, בלי checkout של קוד ה-fork), מגדירים מדיניות Actions שמאפשרת אותו במפורש; אחרת - עוברים ל-pull_request הרגיל עם permissions מצומצמים.

חיבור אפשרי לפרויקטים שלך: אם מענה, dorgames או Podcasto הם (או יהיו) ריפויים ציבוריים עם CI שמקבל PR-ים מבחוץ - בדוק עכשיו ב-Insights של כל ריפו אילו ריצות היו נחסמות, לפני ה-brownout הראשון ב-9.11. חלון השבועיים הוא בדיוק הזמן לתקן בלי לחץ.

023.11: Claude Code 2.1.317 - בלימת דליפת אימייל לרשת, hooks עם onFailure: "block", ודוח עלויות ל-gateway+

מה זה ולמה כאן

שוחרר ב-3.11 (לילה). גרסה עם נטייה ברורה לפרטיות ושליטה ארגונית: שני מנגנוני בלימת-דליפה חדשים, חיזוק מודל ה-hooks, וכלים לניהול עלויות צוות. משמעותית לכל מי שמריץ סוכנים עם גישה לרשת.

שלוש הבטיחות

אחת: בדיקה חדשה ששואלת אותך לפני שקריאת web או shell שולחת את כתובת האימייל של החשבון שלך לרשת. שתיים: אזהרה ב-/schedule כשמשימה מתוזמנת בענן מקבלת connectors שלא ביקשת - עם הוראות הסרה. שלוש: Agent SDK hooks מקבלים onFailure: "block" - callback שנכשל חוסם את הפעולה במקום לתת לה לרוץ (עד כה ברירת המחדל הייתה fail-open, שזו בדיוק התנהגות שguardrail לא אמור להיות).

ארגוני ותיקונים

מאפייני OTel חדשים (plan, seat_type, provider, custom_base_url), ו-API דוח עלויות ל-Claude apps gateway: GET /v1/organizations/analytics/cost - סה"כ, פר מפתח, פר יום או פר קבוצת IdP, עם שמירת מיפוי יומי של קבוצות. בתיקונים: פרידה של שרתי MCP מקומיים אחרי התור הראשון בסשני Desktop, באג שיכול היה לנתק אותך אחרי claude auth status איטי, והתעלמות מ-effortLevel של הפרויקט בסשנים שנפתחו מראש.

חיבור אפשרי לפרויקטים שלך: אם בנית hooks מגנים על מענה או dorgames (למשל חסימת כתיבה לנתיבים רגישים) - עבור ל-onFailure: "block" מיד; fail-open ב-guardrail הוא אשליה של הגנה. ובדיקת האימייל רלוונטית ישירות: סוכן שרץ עם הפרופיל שלך ומדבר עם שרתי MCP חיצוניים היה יכול להדליף את זהות החשבון בלי שום אירוע חריג.

מקורות: release notes רשמיים (3.11)

032.11: AWS מזקקת סוכן קניות חזיתי ל-Qwen3.5-4B - הציון עולה מ-0.297 ל-0.541, בגובה המורה+

מה זה ולמה כאן

פוסט טכני מלא בבלוג ML של AWS (2.11): צינור זיקוק (distillation) מקצה לקצה לסוכנים - ממודל חזיתי יקר למודל 4B זול, בלי לוותר על איכות המשימה. זו התשובה המעשית לשאלה שכל בונה סוכנים שואל: מתי מותר להוריד דגם?

הצינור

המורה, GLM-5.3 על Bedrock, משחק את סוכן ה-ShoppingBench על סט האימון ומייצר מסלולי פעולה; ה-scorer הפרוגרמטי של ה-benchmark שומר רק מסלולים שפתרו את המשימה; על המסלולים המסוננים מבצעים SeqKD fine-tuning לתלמיד Qwen3.5-4B ב-serverless SFT של SageMaker; הערכה על פיצול held-out; והגשה מאחורי endpoint שמריץ את לולאת הכלים. העיקרון הכרוך: סינון לפי תוצאה, לא לפי "מסלולים יפים" - המורה מייצר גם זבל, וה-grader מסנן אותו.

המספרים, עם ההקשר

ממוצע הצלחה על שלוש משימות (product/shop/voucher): בסיס Qwen3.5-4B 0.297; תלמיד מזוקק 0.541; המורה עצמו 0.540 (greedy) / 0.511 (sampled); מודל חזיתי בינוני 0.546. כלומר ה-4B שיחזר את כמעט כל איכות המורה בתוך רעש ריצה. ההערכות של AWS עצמה: אלו תוצאות benchmark אחד (ShoppingBench) עם scorer פרוגרמטי - הכללה למשימות בלי grader אוטומטי דורשת grader משלך, והמורה דווח בשתי צורות בגלל שגדולת הדגימה משפיעה על ההשוואה.

חיבור אפשרי לפרויקטים שלך: אם ל-Podcasto או מענה יש משימת סוכן צרה וחוזרת (ניתוב, חילוץ, סיווג מובנה) - זו המתכונת: מורה חזק מייצר מסלולים, grader דטרמיניסטי מסנן, תלמיד קטן מקבל את הכל. התנאי הוא scorer אמין; בלעדיו הזיקוק מנחז את הטעויות של המורה בדיוק כמו את ההצלחות.

מקורות: AWS Machine Learning Blog (2.11)

042.11: Scaling Git at OpenAI - Pando, הבקאנד שבנו כשסוכני Codex שברו את הגיט שלהם (5x push, פטה-בייט ביום)+

מה זה ולמה כאן

פוסט הנדסי עומק של OpenAI (2.11, מאת Aaron Friel, Taylor Blau ו-Ted Nyman): כשהמונוריפו שלהם התחיל לסבול מ-reliability של פחות מ-90% תחת עומס שייצרו סוכני Codex (סניפים, pushes, merges ו-clones במקביל בקנה מידה חדש), הם בנו Pando - בקאנד חדש ל-Git, תואם פרוטוקול ולקוח, שמניע היום את כל הפיתוח שלהם.

שתי ההחלטות המרכזיות

אחת: עצמאות פר-סניף - עדכון ref מתואם לכל branch בנפרד, אז pushes לסניפים לא קשורים רצים במקביל (בניגוד לסידור גלובלי דרך 3PC או WAL משותף); המחיר הוא שקורא של כמה סניפים יכול לראות אותם בנקודות זמן שונות. שתיים: שימוש חוזר ב-packfiles - במקום pack מותאם לכל לקוח, אותם בתים מוגשים מה-cache להרבה קוראים; לקוח אולי מוריד אובייקטים שכבר יש לו, אבל השרת כמעט לא מחשב. התוצאה: חיתוך push latency החציוני פי ~5, וכמעט פטה-בייט של נתוני Git ביום.

איך לקרוא את זה

השורה החשובה היא הסיבה, לא המוצר: "היקף העבודה המקבילה שסוכנים מאפשרים" שובר הנחות תשתית שנבנו לקצב אנושי - ראשון הגיט, אחר כך ה-CI, ה-review, וה-deploy. OpenAI גם מדגישה שהשאירה תאימות מלאה ל-Git בכוונה: שיפורי לקוח שהם עושים יכולים לזרום upstream ולהועיל לכל האקו-סיסטם, לא רק להם.

חיבור אפשרי לפרויקטים שלך: ברמתך הנוכחית לא תצטרך Pando - אבל הכיוון נכון לזכור: ברגע שסוכנים כותבים קוד במקביל על מענה או dorgames, צוואר הבקבוק עובר מ"מהירות כתיבת קוד" ל"קצב merges, CI ו-review". שווה לתכנן את צנרת ה-merge (סניפים קצרי-חיים, CI מהיר על כל push) עוד לפני שהעומס מגיע.
