01Claude API 2026-10-21: הגרסה הראשונה מאז 2023 מסירה temperature, top_p ו-top_k+

מה פורסם

ב-21.10 Anthropic פרסמה את גרסת ה-API המוצמדת החדשה 2026-10-21, הראשונה מאז 2023-06-01, עם מדריך מיגרציה מסודר ב-platform.claude.com. זו גרסה שוברת, והיא מגיעה עם דור חדש של SDKs שמשתמשים בה כברירת מחדל.

מה נשבר

שלושה שינויים שמחזירים 400: בקשה ששולחת temperature, top_p או top_k נכשלת גם בערך ברירת המחדל; בלוק document ישירות בהודעת assistant נכשל (ב-user מותר); ובלוק text עם citations לא ריק בהודעת user נכשל. בלי הפרמטרים הדגימה היא בברירות המחדל (temperature 1.0). מודלים כמו Claude 4.7 ומעלה כבר קיבלו רק ברירות מחדל, אבל במודלים כמו Sonnet 4.6 הורדת temperature מאבדת את אפקטה ושום הגדרה אחרת לא מחליפה אותה. מי שמסתמך על דגימה לא-ברירת-מחדלית יכול להשאיר את הבקשות האלה על 2023-06-01.

ה-SDKs החדשים

Python 2.0.0 (פורסם ב-21.10 ב-15:51 UTC), TypeScript 1.0.0, Go 2.0.0, Java 3.0.0, C# 13.0.0 ו-ant CLI 2.0.0 שולחים את הגרסה החדשה כברירת מחדל. שתי מלכודות: ב-Go נתיב המודול משתנה ל-/v2 והנתיב הישן ממשיך להתקין v1 בשקט בלי אזהרה; והרישיון משתנה מ-MIT ל-Apache 2.0 (אומת ב-commit של ה-LICENSE במאגר ה-Python SDK ב-21.10). בנוסף ה-SDKs שולחים את המפתח כ-Authorization: Bearer במקום X-Api-Key; ה-API מקבל את שניהם, אבל פרוקסי או gateway שקורא או כותב X-Api-Key צריך לעבור (Foundry עדיין שולח x-api-key).

באותו יום: אכיפה לפי לקוח קצה

User profiles ב-API קיבלו שדות enforcement_status ו-enforcement_actions (Python SDK v2.1.0, 22:00 UTC), כך שפעולת אכיפת בטיחות יכולה לנחות על לקוח קצה אחד ולא על כל הארגון. לבאקאנד שמשרת משתמשים רבים דרך מפתח אחד, זה משנה את מפת הסיכון.

חיבור אפשרי לפרויקטים שלך: אם מענה או Podcasto קוראים ל-Claude API, שלוש הפעולות המיידיות: לנעוץ את ה-major של ה-SDK כדי ששדרוג תלות אוטומטי לא יפיל פרודקשן, לחפש בכל הריפו temperature ו-X-Api-Key, ולהחליט לכל קריאה שהורידה temperature אם נשארים על 2023-06-01 או עוברים לניסוח קשיח (JSON Schema) במקום. זו הצעה, לא דיווח על שימוש קיים. הסתייגות: קראנו את מדריך המיגרציה ורישומי ה-SDK; לא הרצנו שדרוג.

02Claude Code 2.1.307: שכבות הבטיחות הופכות לאירועי טלמטריה+

מה פורסם

גרסה v2.1.307 ב-21.10 ב-22:17 UTC. שלושה דברים בה שווים קריאה, והראשון הוא מבני: אירוע OpenTelemetry חדש, claude_code.safety_event, שנורה על כל קריאת כלי שכלל הרשאה, auto mode, בדיקת בטיחות, hook או ה-sandbox עצרו, ביקשו אישור או החזירו. אחרי שייצוא OTEL נכנס לבטא ב-14.10, עכשיו אפשר לספור אירועי בטיחות לפי כלל: כלל שמבקש אישור כל הזמן כנראה הדוק מדי, וכלל שלא יורה אף פעם אולי לא עושה כלום.

MCP: לא עוד קריאות כפולות

קריאת כלי HTTP לשרת MCP שנשלחה פעמיים כשהחיבור נסגר באמצע לא תישלח שוב, אלא אם הכלי read-only או idempotent. מי שמפעיל שרת MCP משלו צריך לסמן כלים כותבים כ-idempotent או לבנות אותם כך, ולא לסמוך שהלקוח ימנע כפילות. בנוסף: שרתי MCP שהוצגו כ-"needs authentication" ב-macOS כשה-keychain נעול עכשיו מסבירים למה, ותוקן דיווח timeout שגוי כשהמחשב נרדם בזמן חיבור.

עוד שכדאי להכיר

/claude-api api-version מעבירה קוד Claude API לגרסה 2026-10-21 (מחברת ישירות לכרטיס 01). קריאות כלי שלא מתפרסרות מקבלות עד שני נסיונות חוזרים לפני שהתור נגמר בשגיאה. fork subagents שמושקים יחד מקבלים זהות משלהם כדי שלא ינסו להתחיל את העבודה זה של זה. ותוקנו באגי מצב בענן: /clear שחוזר אחרי restart, /autocompact שחוזר לחלון ברירת מחדל, ו-WebFetch ב-Cowork שמדווח 4xx כתוצאה נורמלית.

חיבור אפשרי לפרויקטים שלך: אם אחד הפרויקטים מריץ Claude Code עם OTEL או עם שרת MCP עצמאי (מענה או dorgames, אם בכלל), שני הדברים האלה ניתנים ליישום מיידי: דשבורד שסופר safety events לפי כלל, וסימון כלים כותבים כ-idempotent. זו שאלת בדיקה, לא דיווח על תצורה קיימת. הסתייגות: קראנו את רישום הגרסה ולא הרצנו אותה.

03מודלי OpenAI ותהליכי Codex מגיעים ל-Google Cloud+

מה פורסם

ב-21.10 OpenAI ו-Google Cloud הכריזו על שותפות שמביאה את מודלי החזית של OpenAI ואת תהליכי העבודה הסוכנתיים של Codex ל-Model Garden. הרכישה דרך Google Cloud Marketplace, כולל קיזוז מול התחייבויות GCP קיימות, ובהמשך גם ב-Google Antigravity וב-Gemini Agent. זמינות כללית מתוכננת "בשבועות הקרובים", ומיקרוסופט נשארת שותפת הענן הראשית. זהו ענן מרכזי שני שמוכר את המודלים, אחרי ש-AWS החלה להגיש GPT-6 באסיה-פסיפיק ב-12.10 (לפי סיכום צד שלישי, לא אומת היום במקור).

מה שמעשי לבונים

ההכרזה היא עסקית-תשתיתית, אבל שתי שאלות כבר עכשיו: אילו יכולות יגיעו לערוץ הזה ומתי (למשל, האם ה-12-hour caching של אתמול יופיע שם ובאיזה תמחור), ואיך נראים תהליכי Codex בתוך Model Garden מול ה-API הישיר. מי שיש לו התחייבות הוצאה על Google Cloud יכול לקזז אותה, מה שמשנה את חשבון העלות של פיילוט.

חיבור אפשרי לפרויקטים שלך: שכבת הפשטה מעל ספק המודל (שממנה דיברנו גם במהדורות קודמות) היא שוב התשובה: מי שמחזיק אותה, מעבר ערוץ הוא שינוי קונפיגורציה ולא שכתוב. זו עמדה כללית, לא פעולה ספציפית לפרויקט.

04GitHub CLI v2.103.0: טוקנים מתפוגגים עם ריענון אוטומטי+

מה פורסם

ב-21.10, ב-public preview: gh auth login --expiring (או gh config set expiring_credentials enabled לכל התחברות) נותן טוקן גישה מתפוגג לצד refresh token מסתובב, עם ריענון ברקע. טוקן גישה שדלף הופך חסר תועלת תוך שעות במקום לחיות לנצח. gh auth status מראה מתי הטוקן הנוכחי פג. זמין ב-github.com וב-ghe.com, וב-GHES מגרסה 3.23; בעתיד יהפוך לברירת מחדל להתחברויות חדשות.

שתי נקודות לשים לב

ראשית, לעבודה עם git מומלץ gh auth setup-git כדי ש-gh ישרת את ה-credential, ו-git 2.46 ומעלה כדי שטוקנים מתפוגגים לא יישמרו במטמון מעבר לחייהם. שנית, סקריפטים ששומרים את הפלט של gh auth token לשימוש חוזר יישברו: צריך לקרוא אותו טרי בכל פעם, כי הקריאה עצמה מרעננת.

למה זה חשוב לסוכנים

סוכנים שרצים ב-CI או בענן מחזיקים לעיתים טוקני GitHub ארוכי-חיים, וזה בדיוק הרדיוס שהאיום על התקנת חבילות (מהדורת אתמול, package firewall) מנצל. טוקנים מתפוגגים מקטינים את רדיוס הפגיעה של אותם credentials. גילוי נאות: הרדאר הזה עצמו מתחבר מחדש מדי יום ב-device flow עם טוקן רגיל; מעבר ל-expiring מחכה לבדיקה שהריענון ברקע עובד בסביבה לא-אינטראקטיבית.

חיבור אפשרי לפרויקטים שלך: אם מענה, Podcasto או dorgames מריצים gh או git מעל HTTPS בסביבות אוטומטיות, שווה להפעיל את ה-opt-in ולחפש מקומות ששומרים gh auth token לקובץ או משתנה סביבה. זו הצעה, לא בדיקה של הסביבות שלך.
