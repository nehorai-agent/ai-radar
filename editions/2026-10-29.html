01GitHub Agentic Workflows ב-GA: כותבים אוטומציה ב-Markdown, מקבלים Actions YAML עם סוכן בפנים+

מה פורסם

ב-28.10: Agentic Workflows, פרויקט הקוד הפתוח של GitHub Next, עובר ל-General Availability. מגדירים אוטומציה בשפה טבעית בקבצי Markdown, והכלי מקמפל אותם ל-Actions YAML סטנדרטי - triage של issues, ניתוח כשלי CI, עדכוני תיעוד, כתיבת טסטים. בגלל שאלו Actions רגילים, הם יורשים את runner groups והמדיניות הקיימים. אפשר להריץ עם Copilot או להביא סוכן קידוד משלכם.

שכבות הבטיחות (החלק המעניין)

הרשאות read-only כברירת מחדל, סוכנים רצים בקונטיינר מבודד מאחורי Agent Workflow Firewall, הפלטים עוברים תהליך safe outputs, ו-job ייעודי של threat detection סורק כל שינוי מוצע לפני שהוא מוחל. בגישה לתוכן GitHub חלים כללי integrity filter. זו אותה ארכיטקטורת "תכנן-בודק-מאשר" שראינו ב-Assist של OpenAI ובהכילה של Claude Code - עכשיו כברירת מחדל ב-CI.

מה חדש מאז ה-public preview

תמיכה ב-Actions Runner Controller עם Docker-in-Docker על runners עצמאיים; gh aw forecast יצא מניסיוני עם תחזית תקציב שכוללת קרדיטי threat detection; רענון קטלוג המודלים ובחירת ספק לכל workflow; model routing שמייעל לפי סוג ורמת קושי של המשימה; ובידוד סוכנים ב-micro-VM (Cloud Hypervisor או NVX) עם enclaves שמונעים דליפות בין ריפושיתורים. יש גם gh aw add-wizard לתבניות חדשות.

חיבור אפשרי לפרויקטים שלך: אם למענה או ל-dorgames יש ריפו פעיל ב-GitHub, זו נקודת הכניסה הנקייה לסוכנים ב-CI: Markdown במקום YAML עדין, הרשאות קריאה כברירת מחדל, ותקציב צפוי מראש עם gh aw forecast. תבנית issue-triage היא פיילוט זול לבדיקה. זו הצעה, לא דיווח על תהליך קיים. הסתייגות: קראנו את ההכרזה ולא הרצנו workflow.

02Copilot Fusion ב-GA: לא בוחרים מודל - בוחרים רמת מאמץ, והמערכת מנתבת+

מה פורסם

ב-28.10: Copilot Fusion עובר ל-General Availability. בוחרים "Fusion" בבורר המודלים ורמת מאמץ (Standard / High / Max), ומערכת הניתוב מחליטה לכל prompt אילו מודלים עובדים ואיך. זה שילוב של Project HydraFusion (תזמור רב-מודלי) עם auto model selection של Copilot.

שלוש תבניות התזמור

Single: מודל אחד פותר ישירות. Cascade: מודל חסכוני מנסח טיוטה, בדיקת איכות מחליטה אם לקבל או להסלים למודל חזק. Critique: מודל אחד מנסח, אחר סוקר, והראשון מתקן. לפי GitHub, Fusion Max הגיע ל-60 ב-Artificial Analysis Coding Agent Index - נקודתיים מ-Claude Code עם Opus 5.5 Max - בחצי עלות API למשימה, חצי טוקנים ו-40% פחות זמן. הסתייגות: זו מדידת vendor על benchmark ציבורי, לא אימות עצמאי.

בקרות ארגוניות

אדמינים קובעים מאילו מודלים Fusion רשאי לבחור (במדיניות המודלים של הארגון), יכולים לחסום מודל מסוים רק ל-Fusion בלי לחסום אותו לכולם, ולהגדיר Fusion כברירת המחדל. החיוב לפי רמת המאמץ.

איך לקרוא את זה

המהלך מעביר את "בחירת המודל" ממך למערכת - בדיוק הבעיה ש-Podcasto פתר השבוע בצד שלו עם רג'יסטרי קנוני ו-resolver לפי תפקיד (writer/brief/judge). ההבדל המעניין: ב-Podcasto הבחירה קבועה לפי תפקיד ושקופה לך; ב-Fusion היא דינמית לכל prompt ואטומה. שני הכיוונים חוקיים - אחד נותן שליטה וחיזוי עלות, השני נותן אפס החלטות.

חיבור אפשרי לפרויקטים שלך: ה-Cascade של Fusion הוא בדיוק דפוס "מודל זול מנסח, חזק בודק" שמתאים ל-pipeline של תסריטים ב-Podcasto - שווה לשקול כניסוי מול הבחירה הקבועה הנוכחית, עם מדידת עלות מול איכות. זו הצעה, לא דיווח על שינוי קיים.

03Copilot Memory ב-GA ו-"dreaming" ב-preview: סוכן שזוכר בין סשנים - ומטפח את הזיכרון לבד+

מה פורסם

dreaming - שלושה סוגי "חלומות"

טיפוח זיכרון אישי לפי שיחות הסוכן, ניהול זיכרונות ברמת ריפו, וניהול custom instructions. כלומר: תהליך רקע שמסדר את ההקשר בין סשנים במקום שהוא יצטבר כמו CLAUDE.md שאף אחד לא מנקה.

המספרים והבקרות

לפי GitHub, בסשני CLI שנסקרו ב-preview, 93% הראו עמידה טובה יותר בהעדפות המפתח ו-42% workflows יעילים יותר (מדידת vendor). זיכרונות אישיים ניתנים לצפייה ומחיקה בהגדרות. החלק השלישי בחבילה - Code Search מעבר ל-checkout - מרחיב את ההקשר לריפושיתורים קשורים.

איך לקרוא את זה

הזיכרון הופך לשכבת מוצר רשמית עם ממשק ניהול - לא עוד קובץ טקסט בריפו. השאלה הפתוחה היא מי שולט במה שהסוכן "למד" אוטונומית: dreaming שמטפח זיכרונות לבד הוא גם מנגנון שיכול לקדד טעות. ממשק הצפייה/מחיקה הוא התשובה של GitHub; שווה לעקוב איך זה עובד בפועל.

חיבור אפשרי לפרויקטים שלך: אם אתה עובד עם Copilot על מענה או dorgames - הפעלת Memory והגדרת זיכרון ריפו אחד (פקודת הטסטים הנכונה, מוסכמת code review) היא ניסוי זול עם תשואה מיידית. הדפוס "זיכרון מנוהל + טיפוח רקע" רלוונטי גם לחשיבה על הקשר מתמשך במוצרים שלך. זו הצעה, לא דיווח על שימוש קיים.

04שרתי ה-MCP הרשמיים v2.2.0: עדכון אבטחה אחרי פריצת ה-CA של eMudhra - מי צריך לפעול+

מה פורסם

ב-28.10: גרסת v2.2.0 לריפו שרתי הייחוס של MCP. ההקשר: ב-20.10 eMudhra גילתה שמפתחות פרטיים של שמונה תעודות CA ביניים שלה ניתנים לשחזור מהתעודות הציבוריות; ב-21.10 Node.js שחררה עדכוני אבטחה שמעדכנים את מאגר ה-CA המובנה (ומתקנים CVEs חמורים נוספים); וב-23.10 certifi 2026.10.23 הסיר את שורשי eMudhra.

איפה שרתי ה-MCP עומדים

שרתי ה-TypeScript (everything, filesystem, memory, sequential-thinking) לא נושאים תעודות CA משלהם - הם סומכים על ה-Node.js שמריץ אותם, ורק server-everything יוצא לרשת בכלל. mcp-server-fetch (פייתון) מאמת HTTPS מול certifi דרך httpx - ה-Dockerfile עודכן ל-certifi 2026.10.23. mcp-server-git ו-mcp-server-time לא מתחברים לרשת.

מה צריך לעשות בפועל

מריצים שרת TypeScript מ-npm (npx או התקנה גלובלית)? שדרגו את Node ל-24.22.1 או 26.12.1 ומעלה - שדה ה-engines של החבילות מקבל כל Node 24, אז npm לא יזהיר על runtime ישן ופגיע. מריצים mcp-server-fetch מסביבה שנוצרה לפני 23.10? uvx --refresh mcp-server-fetch או pip install -U certifi.

חיבור אפשרי לפרויקטים שלך: שרת ה-MCP של Podcasto רץ על Node - בדיקת גרסת ה-Node בפרודקשן מול 24.22.1/26.12.1 היא פעולה ישירה מהעדכון הזה. זו שאלת בדיקה, לא דיווח על תצורה קיימת.

05מדידה: שורת הסטטוס של Claude Code שורפת ~16% מהטוקנים - ותיקון עוקף ב-Bun preload+

מה פורסם

ב-29.10 (Gist + דיון ב-HN): מדידה של Flamerix AI מראה שכל ~30 שניות, לכל סוכן רקע, Claude Code שולח את כל הטרנסקריפט של הסוכן למודל שלו (בדרך כלל Opus) ומבקש "תאר את הפעולה האחרונה ב-3-5 מילים" - רק כדי לעדכן את שורת הסטטוס בפאנל הסוכנים. אין הגדרה שמכבה את זה, ומאז 2.1.232 זה דולק כברירת מחדל.

המספרים

בשבוע מדוד אצלם: agent_summary היה 16.4% מהעלות המוערכת (השיחה הראשית: 15.7%), 19.7% מכלל הבקשות, ~9,000 טוקני קלט על כל טוקן פלט. איסוף ארבע מדידות עצמאיות ב-issue 86879 נותן 18-26%. הסתייגויות חשובות מהדיון: רוב הקריאות פוגעות ב-prompt cache אז העלות האמיתית נמוכה יותר; בודק עצמאי אחר מדד ~8% לכל היותר, בעיקר בסוכני משנה עם הקשר ארוך (workflows לא מושפעים); ו-Flamerix מוכרים את DRIM, מערכת המדידה עצמה - מדידת vendor, לא מכון תקנים. במנוי, מה שמבזבזים הוא בעיקר headroom של rate limits.

התיקון העוקף

no-agent-summary.js - preload של Bun ב-~80 שורות שעוטף את setTimeout/setInterval ומנטרל רק את הטיימר של הסיכום (מזהה לפי עוגני טקסט בקוד ה-callback). מותקן דרך BUN_OPTIONS=--preload, נבדק על לינוקס ב-2.1.257-2.1.312, עם מצב A/B (CC_AGENT_SUMMARY_MODE=pass) ורישום אימות. הקו הפרודים: התאמה היא לפי טקסט מקור - עדכון של Claude Code יכול לשבור אותה בשקט ולהחזיר את הבזבוז, אז צריך לאמת מחדש אחרי כל עדכון.

חיבור אפשרי לפרויקטים שלך: אתה מריץ Claude Code עם סוכני רקע - אם ייצאת ל-OTel, בדיקת query_source = agent_summary אצלך היא דרך לדעת בחמש דקות כמה זה עולה לך בפועל לפני שמתקינים hooks על הבינארי. זו שאלת מדידה, לא המלצה גורפת. הסתייגות נוספת: לחברה שפרסמה יש אינטרס מסחרי במדידה גבוהה.
