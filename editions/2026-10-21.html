01Claude Code 2.1.305–306: תיקון לרגרסיה של אתמול, ושער חדש ב-sandbox+

מה פורסם

שתי גרסאות תוך שבע שעות: v2.1.305 ב-20.10 ב-20:46:50 UTC (23:46 בישראל) ו-v2.1.306 ב-21.10 ב-03:16:31 UTC (06:16 בישראל). 305 היא גרסת תוכן עם רשימה ארוכה; 306 מכילה שני תיקונים בלבד. הרישום הראשון שכדאי לקרוא הוא תיקון לרגרסיה שהגיעה דווקא מ-v2.1.304, הגרסה שכוסתה במהדורת אתמול.

1. תיקון לרגרסיית tool search מ-2.1.304

מאז 2.1.304, כל בקשה יכלה להיכשל ב-Vertex, Bedrock וספקים אחרים כשה-endpoint או gateway דחה את tool search, או כש-ToolSearch נחסם או הושמט מ---tools. מעכשיו Claude Code מנסה שוב בלעדיו. מי שהסבים שלו נשברו אתמול מאחורי gateway, זה התיקון.

2. sandbox.allowNestedUserNamespaces

הגדרה חדשה שמאפשרת לפקודות ב-sandbox על לינוקס ליצור user namespaces (נדרש ל-Chromium ול-podman חסר-הרשאות). הרישום אומר במפורש שזה מאפשר להן לעקוף את הגנות הקבצים של ה-sandbox. כלומר: זו דלת שפותחים ביודעין כדי שכלים מסוימים יעבדו, לא שיפור אבטחה. ההחלטה אם להפעיל היא החלטת סיכון, לא ברירת מחדל.

3. תיקוני MCP ותזמון

שרת MCP שהועבר מסשן ענן או מ-setMcpServers של ה-SDK לא יוחלף עוד באמצע הסשן בשרת בעל אותו שם מההגדרות האישיות. דיאלוגי ההסכמה של MCP שופרו כך ש-Enter שהיה מיועד לפרומפט לא יתקבל בטעות כאישור. ו-CLAUDE_CODE_RETRY_WATCHDOG_USAGE_LIMIT_RECHECK_MS מאפשר למצב retry ללא השגחה לשים לב שמגבלת שימוש הוסרה לפני ה-reset. ב-306: claude -p בסשני ענן לא מדווח עוד "Not logged in" כשהוא מופעל בלי משתני הסביבה של הסשן, ושגיאת API לא תוחלף עוד ב-"prompt is too long" עם compaction מיותר בסשנים עם הרבה כלי MCP.

עוד ששווה להכיר

Workflow resume לא מריץ מחדש agents של pipeline() ו-parallel() שכבר הושלמו, אלא משרת אותם מה-journal של הריצה. תיקוני worktrees (סניף ברירת מחדל במאגר bare, ניקוי worktrees של subagents), והודעת ENOSPC ברורה כשהדיסק מלא.

חיבור אפשרי לפרויקטים שלך: אם מענה או dorgames מריצים Claude Code מעל Vertex/Bedrock או מאחורי gateway, 2.1.305 הוא עדכון שכדאי לקחת מיד, כי הרגרסיה מ-2.1.304 יכלה לשבור בדיוק אותם. זו שאלת בדיקה, לא דיווח על תצורה קיימת. הסתייגות: קראנו את רישומי הגרסה ולא הרצנו את 305/306.

02GitHub package firewall ב-public preview: בדיקת npm בין הסוכן לרישום+

מה פורסם

ב-20.10 GitHub הכריזה על package firewall ב-public preview לכל לקוחות GitHub Enterprise Cloud, כולל data residency. הרקע: מתקפות נוזקה שפוגעות בזמן התקנת חבילה, וקוצפות credentials ממכונות CI/CD ומתחנות מפתחים בלי להריץ את קוד החבילה בכלל.

איך זה עובד

ה-firewall יושב בין נקודות קצה כמו runners של Actions או סוכני קוד לבין רישומי החבילות, ובודק גם בקשות metadata וגם הורדות בפועל. האדמין מגדיר מדיניות: cooldown (חבילה שנפרסמה לפני X זמן לא נכנסת), בדיקה מול GitHub Advisory Database לנוזקות ופגיעויות, ובדיקות שרשרת אספקה כמו attestation downgrades. חסימה שגויה מטופלת בבקשת חריגה בזרימה דומה ל-GitHub Advanced Security.

זמינות ומגבלות

חינם במהלך ה-preview; ב-GA יתומחר כשימוש מדוד, בדומה ל-Actions. כרגע npm בלבד. נקודות הקצה (סוכנים, CI) צריכות להיות מוגדרות לנתב דרך ה-firewall במקום ישירות לרישום.

למה זה משנה לבוני סוכנים

סוכני קוד מתקינים תלויות בעצמם, בתוך סביבות שמחזיקות סודות, וזה אחד הפערים הכי פחות מכוסים. ההכרזה היא רק ל-Enterprise Cloud, אבל שתי הפעולות שהיא מרמזת עליהן פתוחות לכולם: cooldown שמונע מ-npm למשוך גרסה שפורסמה לפני שעות, והימנעות מהזרקת credentials של פרודקשן בזמן שסוכן מתקין חבילות.

חיבור אפשרי לפרויקטים שלך: אם אחד הפרויקטים מריץ סוכן שמבצע npm install אוטונומי (ב-CI של מענה או dorgames, למשל), שתי הפעולות האלה ישימות היום בלי Enterprise. זו הצעה כללית, לא בדיקה של ה-CI שלך.

03tsrs: פורט של TypeScript ל-Rust, והחידוש האמיתי הוא איך מתחזקים אותו+

מה פורסם

ב-20.10 Cloudflare ו-VoidZero (יחד עם Max Schwenk מ-Owner.com) הציגו את tsrs: פורט של קומפיילר TypeScript ל-Rust, בעבודה צמודה עם צוות TypeScript ובתוך ארגז הכלים Oxc. לא fork: צוות TypeScript נשאר הבעלים היחיד של השפה. גרסה ניסיונית זמינה כבר ב-npm (npm install tsrs).

המספרים (בהסתייגות יצרן)

על פי הבלוג: עד פי 8 מהר יותר וכ-70% פחות זיכרון מ-TypeScript 7.0 באותו מספר workers, ו-TypeScript 7.1 beta מהירה פי 2.5 מ-7.0, חלקו בזכות אופטימיזציות שהועלו מ-tsrs ל-upstream. הפעם הבנצ'מרקים תואמו מול צוות TypeScript כדי שיהיו באותה תצורה, אחרי שבנצ'מרקים קודמים של פורטים הושוו תצורות שונות. עדיין: אלה מספרי המפרסמים, לא בדיקה עצמאית.

למה עכשיו, ולמה Rust

התשובה שלהם ישירה: מודלי AI של חזית יכולים היום לבצע פורטים בקנה מידה גדול כמעט בעצמאות תוך ימים. Rust נבחר בגלל WebAssembly: בלי GC של Go, אפשר להריץ את כל שרשרת הכלים בסביבה מבודדת על Workers, בדפדפן או במכשיר embedded, מה שמתאים להרצת סביבות פיתוח שלמות בתוך לולאות סוכנים.

שיטת התחזוקה היא הסיפור

הם מיישמים את שיטת Vinext: בכל בוקר סוכן סוקר את השינויים ב-upstream, שולף diffs ופותח tracking issues; בכל לילה נבנית מחדש מטריצת תאימות מהרצת חבילת הבדיקות של TypeScript; וכשמתגלה פער, סוכנים מאתרים את השינוי בשני בסיסי הקוד, בונים רפרודקשן, מייבאים בדיקות ומציעים תיקון. בנוסף הם ממזגים את tsc-rs של Theo Browne לתוך tsrs כדי לכסות גם LSP. כרגע יש פערים ידועים, למשל סדר ההדפסה של diagnostics.

חיבור אפשרי לפרויקטים שלך: השיטה רלוונטית לכל פרויקט שרודף אחרי upstream (תוספים, שכבות תאימות, SDK): סוכן יומי על ה-diff פלוס מטריצת בדיקות לילית היא תבנית שאפשר להעתיק בלי Cloudflare. ל-dorgames עם שרשרת TypeScript, אפשר להריץ tsrs לצד tsc ב-CI על ריפו אחד גדול ולהשוות זמן ו-diagnostics, בלי להחליף את הבדיקה האמיתית. אלו הצעות, לא דיווח על שימוש קיים.

04OpenAI מוסיפה prompt caching ל-12 שעות: החשבון של קידום נקודת השבירה+

מה פורסם

ב-20.10 נוסף ל-changelog של ה-API: אפשר לבחור prompt caching ל-12 שעות ב-Responses API, כדי שהוראות, כלים וקונטקסט משותפים יישארו במטמון גם כשהבקשות במרחק שעות זו מזו, עם תמחור קלט מהמטמון. לפי מדריך ה-prompt caching הרשמי: כתיבה ל-30 דקות (ברירת המחדל) עולה 1.25x ממחיר טוקן קלט רגיל, כתיבה ל-12 שעות עולה 2.5x, וקריאה מהמטמון 0.1x ברוב הדגמים ו-0.05x ב-GPT-6.1 Sol, בלי תלות במשך החיים שנבחר.

החשבון שצריך לעשות

השאלה היא כמה פעמים prefix משומש מחדש לפני שפג. במחירי הקריאה האלה, כתיבה אחת של 30 דקות ושימוש חוזר מלא אחד עולים 1.35x מול 2x בלי מטמון; עשר בקשות עם כתיבה אחת ותשע קריאות מלאות עולות 2.15x מול 10x. כתיבת 12 שעות משתלמת רק אם יש מספיק שימושים חוזרים לאורך החלון הארוך; שדרוג כיסוי קיים של 30 דקות ל-12 שעות מחויב ככתיבת 12 שעות חדשה, בלי זיכוי על הקודמת. במצב explicit אפשר לשלב עד ארבע נקודות שבירה בבקשה, ולשים prefix יציב ל-12 שעות ותוכן משתנה על 30 דקות. שים לב: שינוי ב-tools, בסדר הכלים או ב-parallel_tool_calls שובר את ההתאמה של ה-prefix.

למה זה משנה לסוכנים

סוכנים מחזיקים system prompt וכלים ארוכים שחוזרים כל היום. עד עכשיו פער של שעה בין קריאות איבד את המטמון; עכשיו אפשר לשמור את ה-prefix היציב חי 12 שעות ולנהל את החלק המשתנה בנקודות שבירה קצרות. זו המשך ישיר של פרסום אתמול של Cloudflare על חיתוך עלויות סקירת קוד ב-68% בעזרת מיקום נקודת שבירה (פרסום מ-20.10 שלא נקלט למהדורה בעיתוי): העלות יורדת ממבנה הפרומפט, לא מהחלפת מודל.

חיבור אפשרי לפרויקטים שלך: אם Podcasto או מענה קוראים ל-Responses API עם הוראות מערכת ארוכות ומרווחים ארוכים בין קריאות, שווה לבדוק כמה שימושים חוזרים ביום יש ל-prefix המשותף לפני שמשלמים 2.5x על כתיבה. זו הצעת חשבון, לא דיווח על שימוש קיים. הסתייגות: הפרטים מהמדריך הרשמי נכונים ליום הפרסום; לא הרצנו מדידת עלויות.
